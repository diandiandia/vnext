# vNext 设计改进建议：借鉴 Cloudflare Security Audit Skill

日期：2026-11-04

状态：已获准开发；本地实现及验证，外部效果／宿主验收未完成

修订：用户已批准按编号实施，并选择“版本化计划扩展”；新增策略保持显式 opt-in

vNext 基线：`a0d3179`
参考仓库：`https://github.com/cloudflare/security-audit-skill`，本地版本 `c1c8a8c`

## 1. 提案目的与边界

本提案回答：哪些设计值得吸收、应该接入哪里、如何避免重复建设，以及怎样验证改进有效。
第 1–13 节保留设计与任务验收条件；第 14 节区分实际实现、验证及阻塞。
它不是发布承诺、具体目标的审计计划或新的发现指令。
不得把本文整篇放入 R1/R2 发现任务上下文。

总体方向：

> 保留 vNext 的事件、任务、修订、证据和恢复内核，
> 改善审计注意力分配、覆盖补漏、预算规划和报告交付。

当前评估及限制见[通用性评估](GENERALITY_REVIEW_VNEXT.md#latest-review-2026-11-04-generality-and-evaluation-integrity)。
本提案不宣称 Google 内部验收、ISO/IEC/IEEE 12207 符合性或无偏见发现能力。

## 2. 建议总览

优先级表示建议顺序，不代表已经批准；P0 也不是立即修改默认行为的授权。

| 编号 | 建议 | 优先级 | 建议处理 |
|---|---|---|---|
| A | 独立覆盖复核 Coverage Critic | P0 | 原型验证后显式启用，区分重审与待设计的覆盖扩展 |
| B | 按边界选择领域指导 Domain Companions | P0 | 小范围试点，领域指导与机制卡分层 |
| C | 未决项交付规范 | P0 | 复用 Review Queue，区分调查优先级与严重性 |
| D | 跨阶段预算预留 | P1 | 复用预算和成本预测，新增前置调度准入 |
| E | 可信产物转存与宿主隔离契约 | P1，独立工程 | 单独设计及验证，不用提示词冒充隔离 |
| F | 局部咨询与完整审计入口区分 | P1 | 简化交互，不能绕过完整审计门槛 |
| G | 身份与去重规则复核 | P2 | 针对具体歧义补测试，不全面迁移 ID |

## 3. 必须保留的架构约束

1. 保留 Campaign、Batch、Work Unit、Handoff、任务租约、事件及内容寻址证据。
2. 不创建第二份覆盖账本或另一套相互竞争的判决状态。
3. 不静默修改已冻结 Campaign 的知识、范围、预算策略或任务语义。
4. 独立审计仍默认 `fresh`；历史发现只能通过显式 `follow-up` 关系使用。
5. 不因增加领域材料而减少既有语言支持，或将每语言十项当成发现上限。
6. 不为了降低成本跳过必要验证；允许明确停止和披露不完整。
7. Agent 声明不等于宿主观察，结构校验不等于语义正确，工作流 PASS 不等于无漏洞。
8. 未证实的能力保留限制说明，不用新文档把缺口改写为已完成。

## 4. A：独立覆盖复核

### 4.1 要解决的问题

当前计划已经包含组件、源码分片、边界边、Handoff 和六个发现轴，并非只有语言卡片。
但“已有任务全部完成”不能证明“计划没有漏掉重要工作”。
当前缺少统一的主动补漏规划闭环，见[操作手册的覆盖限制](../ORCHESTRATOR_RUNBOOK.md#6-coverage-and-closing-work)。

### 4.2 建议行为

- 初次复核：相关 R1/R2 已提交当前覆盖结果、进入大规模 R3 验证前。
  不宣称 R1 已识别所有 Surface；复核正是为了发现其遗漏。
- 最终复核：相关 R5 结果和必要恢复处理完成后、R6 及 Campaign 闭合前。
  如复核引发补充工作，完成相应流水线后再判断是否具备闭合条件。
- 复核者只读当前快照及必要的当前覆盖材料，不执行目标代码、不改共享状态。
- 检查遗漏入口、平行路径、生命周期、跨组件契约、缺少证据的排除和错误闭合。
- 返回新增覆盖提案、重审请求及源码依据，不直接判定漏洞或修改计划。
- 协调器验证范围、身份、重复及预算后，按下述处置分类安排工作。
- 显式 follow-up 可检查已声明历史缺口；fresh 不接收历史答案。

不固定照搬 Cloudflare 的双 critic 次数。原型先评估独立复核收益与成本，
再决定是否需要“每轮复核 + 独立最终复核”以及适用范围。

采用协调器调度的专有任务类型，不新增 R2.5 阶段。
`task-schedule-coverage-critic` 只是候选命令名，尚无该接口。
任务需绑定快照、计划及相关阶段修订；上游变化后不得复用旧复核结论。
CG3/CG4 是 Campaign 覆盖门槛，不是 R6 内部的两个检查。
跨 Batch 的最终复核还需覆盖已知跨单元依赖，不能只汇总各 Batch 的“无新增”。

### 4.3 缺口处置与现有能力边界

| 缺口类型 | 建议处置 |
|---|---|
| 已有范围中的漏审或无依据闭合 | 安排有理由的重审，保留历史并正确失效相关下游 |
| 已知跨单元边界的未完成工作 | 按现有 Handoff 的身份、所有权及协调契约处理 |
| 新覆盖义务、新边界或新增范围 | 单独设计受控扩展，明确批准、身份、修订、去重和失效规则 |

现有 [Plan Amendment 校验](../../src/reachable_audit/planning.py)要求
`work_units`、`boundary_edges` 等计划内容保持不变，不能直接追加“微型 Work Unit”。
其 Batch 重组能力不等于任意覆盖扩展能力；新增任务重审的接口也须在实施时验证。
不能为了兼容现有命令而绕过不可变约束，或把遗漏入口直接升级成漏洞假设。
获准新增的发现工作仍需按适用的 R1/R2 契约提供源码锚点和六轴处置。

### 4.4 接入与验收

候选接入面：[规划](../../src/reachable_audit/planning.py)、
[任务执行](../../src/reachable_audit/execution.py)、
[闭合报告](../../src/reachable_audit/campaign_closure.py)。
任务名和返回 schema 在实施设计中确定，本提案不创建新协议。

验收至少覆盖：

- 预设遗漏入口、平行路径和生命周期案例能形成有源码依据的补漏请求。
- 无效、重复、越界或无证据请求不能改变计划；有明确拒绝结果。
- 重审保留旧证据，正确失效相关下游，不覆盖历史完成记录。
- 重试、重启不重复创建工作；预算不足产生可见阻塞或延期。
- 上游修订使旧复核失效；多 Batch、范围扩展及最终复核重入都有回归用例。
- 提案无新增工作只表示本轮没有识别到更多缺口，不输出“无盲区”。
- 在隔离的评测夹具中测量有效缺口发现率、错误提案、额外调用与成本，
  同时比较是否只是重复已有检查；标签不得进入发现者上下文。

## 5. B：领域指导与机制卡分层

### 5.1 建议结构

| 层 | 回答的问题 |
|---|---|
| 领域指导 | 当前系统有哪些边界、应该追问什么、哪些外部事实未知？ |
| 语言知识及机制卡 | 具体失效如何发生、有哪些反证、怎样验证语言语义？ |
| 六个发现轴 | 从入口、机制、状态、变体、边界、差异哪些角度追踪？ |

先选择少量领域试点，例如 AI/Agent、数据生命周期、供应链发布。
这只是建议范围，不是自动扩充既有批准知识目录的决定。

### 5.2 选择与内容规则

- 依据当前源码中的真实信任边界选择领域，不能仅按语言、依赖名或项目标签触发。
- 采用“侦察／清单初选 → R1/R2 源码证据细化 → Critic 检查漏选”的渐进选择。
  R1 标签只是候选输入，不是唯一装载开关；后台任务、构建发布和存储生命周期也可建立依据。
- 若引入 `detected_domains` 等字段，须同时记录源码依据、选择理由、领域／段落身份和知识版本，
  并通过有版本的输出契约接入；本文不直接规定 Surface 的新必填字段。
- 按任务加载必要段落，不向所有 worker 发送全部领域文件。
- 切片保留相应适用条件、核心纪律、反证及验证规则，不能只注入攻击动作。
  记录实际装载的段落及摘要，使任务输入可追溯；超出上下文预算时明确阻塞或拆分。
- 每份指导明确适用条件、不适用依据、核心不变量、反证及外部事实阻塞。
- 领域指导不预设漏洞、严重性、部署默认值或过去目标的答案。
- 适合独立表达的具体机制再提炼成卡片；不把整个领域文件压成一张卡。
- 新知识走现有审查、摘要绑定和版本策略；既有 Campaign 继续使用冻结知识。

当前没有“反证轴”。反证贯穿适用的六轴和 R3/R3.5，不新增第七轴。
例如 AI/Agent 领域既检查权限，也检查操作意图绑定：受害者有权执行某操作，
不意味着其已批准攻击者诱导的这次具体操作。不能仅以“未跨租户”或“工具有权限”排除问题。

### 5.3 验收

正例能按真实边界选择材料；同语言但不存在该边界的反例不加载。
跨领域路径可组合必要材料，且上下文增量可测量。
加入 R1 漏标后仍能从其他当前源码证据补选的用例，避免标签成为自我强化盲区。
通过未见夹具验证实际发现收益、误报及成本，而不只检查关键词命中。
保留原语言和领域外候选；未选材料不能被解释为该领域已审计安全。

## 6. C：未决项交付规范

复用现有 `NEEDS_REVIEW`、Review Queue 和报告派生，不新增平行判决账本。

建议每个对外交付的待验证事项明确：

- 源码支持的主张、受影响边界、相关主体和资源；
- 已建立的事实与尚未建立的事实；
- 精确阻塞项，以及它为什么会改变判断；
- 有界本地验证计划或所有者观察计划，仅列适用部分；
- 当前证据引用、关联任务和后续处理状态。

未决项不展示为漏洞严重性；必要时提供独立的调查优先级及理由。
候选字段 `investigation_urgency` 可使用 P0/P1/P2/P3 或“未评估”，
具体等级含义在实施契约中定义，不以“假设名称含 RCE”自动判 P1。
评估综合当前证据强度、受保护资源、已建立前提、阻塞事实对判断的影响、
验证成本及时间敏感性；不能借紧急度重新包装未证实的严重性。
风险假设只能明确标为假设，不能混入已确认发现统计。
源码证明、行为复现、安全影响和部署条件分开表达；没有动态实验不自动否定严谨静态证据。

被证伪记录保留审计轨迹，但只抑制源码及条件未变的同一失败主张。
源码、条件或证据变化后允许重新评估，不能永久按指纹封禁。

验收：JSON 与 Markdown 一致；未决、证伪、已确认和加固建议清晰分离；
缺失关键下一步时显式提示；不伪造证据填满模板；不会因隐藏严重性而丢失调查优先级。

校验先放在未决记录生产／验证层，要求有实质内容的阻塞项和至少一项适用的验证计划，
而不是仅检查 `has_blocker` 或非 null。对外未决投影不输出漏洞严重性；
不可因此删除原始阶段证据中的历史字段或改写其含义。
当前 CG10 检查闭合内容及范围处置，不是未决包 schema 校验。
是否由闭合门槛汇总新契约违规，须另行设计、版本化并测试。
旧 Campaign 字段缺失应明确披露，不能补假值或无版本区分地阻断恢复。

## 7. D：跨阶段预算预留

### 7.1 现状与增量

vNext 已有任务 `agent_runs`、委派调用预留、测量超限检查和计划成本预测。
建议补充的是 Campaign 级、跨阶段的前置预留和调度准入。

概念关系：

> 可开展的新增发现工作 = 授权余额扣除必需下游验证、覆盖复核及恢复余量后的部分。

这不是统一货币公式：调用次数、Token、费用、并发与墙钟分别评估。
不能直接相加，也不把 Cloudflare 的约 30% 估计固定成产品默认。

### 7.2 行为与验收

- 调度前估算下游 R3/R3.5/R4/R5/闭合成本；运行中按实际消耗及候选量重新评估。
- 假设数量未知时使用明确的估算区间，不把预估值伪装成实际候选数。
  每个受限资源维度的可用余额须足够覆盖本次任务的准入成本，而非仅要求余额大于零。
- 预留不得被普通发现工作占用；并发准入需要原子化，避免重复消费余额。
- 预留、占用、结算和释放应在持久化事务中原子且幂等，保留关联任务／尝试和变更证据。
  不仅向 `campaigns` 添加几个可覆盖余额字段；具体存储结构在实现设计中确定。
- 预算不足先停止新增发现，保留未完成验证和覆盖缺口。
- 重试、失败尝试和委派计入消耗；缺测量不视为零成本。
- 恢复不重置预算；扩额必须显式授权并保留原始限制及结果。
- 定义清楚“Agent 调用”的计量单位，避免与模型请求、工具调用混淆。

用并发争抢、候选暴增、进程重启、测量缺失及授权扩额回归验证。
报告区分估算、内部准入和宿主硬限制；引擎记账不能代替提供方限额或停止活跃进程。

### 7.3 预算不足时允许和禁止的调整

- 允许停止新增发现、缩小后续获批范围、延期或申请扩额，明确保留未完成义务。
- 对尚未调度的工作，可在显式选择且上下文容量适合时使用紧凑六轴模式；
  不修改既有任务身份、覆盖义务或已冻结策略，不自动迁移已调度任务。
- 紧凑模式调用数较少不代表 Token、耗时或总成本必然较低，需要实际测量。
- 禁止因预算不足将全面 Revival Review 自动改成抽样。
  当前默认复核全部初始 `UNREACHABLE`；若无法完成，披露阻塞而非宣称验证链完整。
- 如未来研究其他选择策略，应另行批准、版本化并前瞻评估召回与成本，
  不能作为本提案的自动节流策略。

## 8. E：可信产物转存与宿主隔离

此项单独设计，不能仅在 Skill 中追加“必须沙箱”就宣布完成。
现有托管执行与输出上限可复用；内容摘要校验不替代安全读取。

建议建立：

1. 明确的宿主能力契约：网络、环境、只读源树、scratch 写范围及资源限制。
2. worker/目标进程只写隔离临时区，可信协调器保留最小非敏感证据。
3. 在受支持平台使用可信目录描述符逐级无跟随访问，检查常规文件、
   链接数、身份及大小，限制单文件和累计字节。
4. 防止 FIFO、设备、符号链接及变化中的文件进入普通证据读取流程。
5. 停止并确认相关进程退出后再转存；目标进程不可访问保留证据目录。
6. 平台缺能力时显式阻塞相应动态验证，不降低隔离要求，也不丢弃已有静态线索。

POSIX 原型可使用 Python 原生的 `os.open`、`dir_fd`、`O_NOFOLLOW`、
`O_NONBLOCK` 及 `os.fstat`，但这些 API 的组合本身不是安全证明。
保留的根目录描述符应可信且不可被目标进程继承；逐级验证源和目标目录，
源文件须为常规文件、链接数为 1，读取期间再次执行单文件及累计限额。
目标叶子须排他、安全创建；复制前后检查身份、类型、链接数及大小，失败时清理不完整产物。
属性未变仍不能证明内容未被并发修改，必须实际隔离所有潜在写入者。

候选实现名 `SafeArtifactPromoter` 及异常名均待接口设计确定，
先明确它与内容寻址存储、执行器及宿主的职责，不要求直接塞进现有证据存储模块。
不支持的平台不得回退到普通 `shutil.copy`；明确报告所缺能力。
“安全转存不可用”和“执行隔离不可用”分别记录，只阻塞依赖该能力的动态验证或证据使用，
不自动推翻独立成立的静态证据，也不伪造新的阶段结论。

验收包含特殊文件拒绝、路径替换、超大及增长文件、后代进程残留、
网络和环境隔离、受限输出，以及目标代码不能写保留区。
支持的平台逐项声明；不将无跟随和 `fstat` 检查单独当成完整沙箱。

## 9. F/G：入口与身份规则

### F：更轻的入口

区分局部安全咨询和完整可恢复审计。局部请求不自动创建 Campaign 或报告。
完整审计沿用必需阶段；任何未来快速模式都必须显式声明范围及不足，
不能仅靠少跑验证来变快。默认切换需先批准和测试。

### G：身份规则

保留现有 LOC 和确定性摘要 ID。覆盖义务身份、源码位置和操作幂等键分开处理。
仅对已复现歧义补充规范及测试，不全面替换为 RFC 3986 字符串。
文件路径不得因 Unicode 规范化而静默合并实际不同对象。
新规则不能破坏旧 Campaign 重放及修订绑定。

## 10. 实施顺序与决策点

| 阶段 | 交付 | 进入下一步的条件 |
|---|---|---|
| 0：评审 | 确认本提案范围及优先级 | 用户批准实施范围，不等于批准全部默认变更 |
| 1：原型 | A 的有证据缺口提案、B 的少量领域材料、C 的报告样例 | 正反例有效，成本可测，无重复账本 |
| 2：集成 | 修订失效、恢复幂等、知识冻结、报告一致性与 D 的预算准入 | 定向回归和相关完整回归通过 |
| 3：宿主工程 | E 的实现、平台矩阵及对抗测试 | 隔离和转存能力实际验证，缺失能力明确阻塞 |
| 4：效果评估 | 隔离标签的未见目标比较 | 同范围、同预算条件下比较发现质量、漏项和成本 |

不得仅凭“多了几个 Agent”“增加了卡片”“所有 schema 通过”判断收益。
默认启用阈值应在效果试验前约定，避免看结果后调整标准。
保持[测试计划](TEST_PLAN_VNEXT.md)、[软件需求](SOFTWARE_REQUIREMENTS_VNEXT.md)和
[验收计划](ACCEPTANCE_PLAN_VNEXT.md)与实际行为同步。

### 10.1 原型基准与归因

沿用[发现质量评估协议](DISCOVERY_QUALITY_EVALUATION_PROTOCOL.md)，区分三类材料：

- 已反复研究的真实目标及历史样本：用于功能调试、故障复现和回归，不作泛化收益的唯一证据。
- 独立标注、开发时未见的评测样本：用于比较发现及补漏效果。
- 未触碰的验收留出集：用于后续前瞻判断，不能边调规则边声称保持独立。

候选项目名单不等于已准备完成的冻结、标注基准。先验证快照、授权、标签质量和访问隔离。
历史目标名称、答案、修复和标签不进入 fresh worker；评估员标签与运行材料分离。

建议分组为基线、仅 A、仅 B，必要时再增加 A+B 组合；C 的报告交付效果单独比较。
基线使用 `a0d3179`，实验组记录准确提交及目录版本。
各组保持模型、快照、批准范围、宿主策略和预算可比，随机运行顺序，
使用独立上下文及盲评，按根因去重并保留失败／延期任务在分母中。
若分别量化知识选择与指导内容的作用，应进一步分离处理变量。

### 10.2 指标定义

| 指标 | 定义及限制 |
|---|---|
| 有效盲区召回 | 在预先独立标注的范围内，识别出的真实遗漏覆盖义务 / 标注的遗漏覆盖义务；不等于漏洞召回 |
| Critic 提案准确率 | 独立复核有效且非重复的缺口提案 / 全部缺口提案，另报漏项及重审收益 |
| Token 增量比 | 相对基线增加的 Token / 基线 Token；分母为零或缺测量时标为不可计算 |
| 每新增有效结果的边际成本 | 成本差 / 相对基线新增且独立判定有效的非重复结果数；无新增结果时不伪造比值 |
| 误报负担 | 对同一判定口径下的候选独立审查，报告误报数量及适当比率，不能把未决项直接计作误报 |
| 人工分诊耗时 | 针对 C 的同等内容交付比较记录审阅耗时、结论正确性及遗漏，不称为误报抑制比 |

另报实际调用、墙钟、完成率、范围缺口和各语言／领域差异，展示成对结果及不确定性。
新增覆盖单元、候选、已确认漏洞是不同结果，不能混作一个“有效线索”统计。
接受阈值、样本量和停止规则在试验前确定，不能仅凭增加数量宣布改进。

## 11. 不建议实施的做法

- 不默认把过去审计答案送进 fresh worker。
- 不直接复制 Cloudflare 整套流程、JSON 账本及固定 Agent 数量。
- 不把 critic 无新建议写成“全覆盖”或“无漏洞”。
- 不把领域库名称和“前沿”标签当作发现质量证据。
- 不固定采用 30% 预留，不混淆事后拒收与事前硬限制。
- 不在预算不足时自动抽样削弱复活复核，不以紧凑模式自动替换既有任务。
- 不假定现有 amend 可扩展 Work Unit，不发明不存在的反证轴或误用 CG10。
- 不永久封禁 rejected 指纹，不给未决项伪装成正式漏洞的严重性。
- 不迁移全部 ID，不静默升级已有 Campaign。
- 不将提示词中的沙箱、独立性、转存要求宣传成仓库已实现能力。

- **M1：设计可实施。** CFA-002、CFA-003、CFA-005、CFA-012、CFA-016 完成；
  CFA-004 可因外部样本条件独立阻塞，但不能宣称效果验收完成。
- **M2：原型可观察。** CFA-006、CFA-014、CFA-018 完成，可测量而不默认扩展覆盖或启用新策略。
- **M3：闭环可恢复。** CFA-011、CFA-015、CFA-022 完成，修订、预算及漏选处理可靠。
- **M4：获批范围可交付。** CFA-029 完成；动态执行相关主张须有 CFA-025 的真实宿主证据。
- **M5：效果与启用有依据。** CFA-030 至 CFA-033 按批准范围完成，未达到标准则继续试点或不启用。

若只批准部分方向，CFA-028 至 CFA-033 应明确记录适用子集并在执行前修订依赖，
不得把未批准或受阻任务标记为完成来满足里程碑。上述顺序不承诺工期或调用费用。

### 14.1 已采用的实现契约

- **A：** `coverage_critic.py` 提供 `coverage-critic/v1`，R1/R2 后、R3 前初审，
  当前 R5 后、R6 前终审；协调器显式派发，直接阶段导入也不能绕过门槛。
  输出须声明实际阅读的 Batch 路径和带 LOC 的检查；提案不直接变成漏洞。
  绑定当前快照、Plan、知识选择和相应阶段产物，旧修订不能满足新门槛。
  独立性检查只证明不同 worker ID 的声明，不证明宿主隔离或真实独立推理。
- **已有义务重审／新增覆盖：** 用户选择版本化扩展。`coverage-extend` 只接受
  当前冻结 inventory 中的路径、新边界及已有 Work Unit 重审请求；新源码需要新
  snapshot Campaign。保留旧 Plan/证据，原子记录新 Plan、Batch 替代和扩展事件。
  首版保守重放**全部 Batch**，不复用旧结论，不能称为“只追加微型单元”的廉价增量。
  旧模型不保存最初配置的分片上限，扩展以旧 Plan 实际最大分片／Batch 大小为保守上限，
  不静默恢复更大的默认值。
  所有旧任务须完成或显式取消。失败回滚数据库事实；内容寻址文件／派生导出可能留存，
  但未引用文件不构成有效 Plan。未成立提案可经独立操作者带源码依据逐项驳回，
  保留 Critic 原文；延期不等于关门。
- **B：** 三份原创紧凑指导 `ai_agent`、`data_lifecycle`、`supply_chain`，
  不是复制第三方长文。协调器根据当前 LOC 在 R2 提交前选择，可在 R1 后补选；
  R2 后漏选走批准重放。每块包含纪律、动作、反证和验证边界，按域整体选择，
  不宣称已实现任意长文的自动语义段落切片或自动标签推断。
  摘要冻结，单元 16 KiB、任务合计 64 KiB，超限报错；未选择为 NOT ASSESSED。
  Critic 同时接收当前选择及漏选检查约束。
- **C：** `review-plan` 复用 Review Queue，绑定当前证据，要求实质 blocker、
  local/owner 验证步骤及调查优先级理由；拒绝 severity 等额外字段。
  P0/P1/P2/P3/NOT_ASSESSED 是调查优先级，不是严重度；旧记录明确显示缺失，
  不伪造计划、不抹去原始阶段证据、不改变 CG10 定义。
- **D：** `task_budget.py` 的事件型逐尝试预留、计量、结算、释放及单调扩额；
  claim 在事务中竞争余额，下游及 Critic 有显式保护额度。估算由操作者配置，
  不是自动按候选数量预测成本。缺测量不免费，失败／重试不清零；不足停止准入，
  不自动改变 R2 模式或抽样必要复活复核。内部准入不等于供应商硬限额。
- **E：** POSIX dirfd/no-follow、常规单链接文件、排他目标、读中限额及失败清理；
  stdout/stderr 使用预先打开的捕获描述符。写入者停止是转存的必要前提，不能靠
  fstat 证明。`host-capabilities` 将安全转存与隔离分开报告；
  `harness-run --isolation linux-bwrap` 在能力或完整策略未验收时拒绝执行，不回退。
  本机真实探测为内核不允许创建所需 namespace，因此未执行目标代码。
  **尚未完成 CFA-025 的真实隔离执行／对抗验收。**
- **F/G：** Skill 区分局部审计咨询和完整流程；局部不自动建 Campaign，也不宣称
  审计完成。位置锚点、语义覆盖义务和任务幂等身份不合并；补 Unicode 路径／元组顺序
  回归，未作无证据的全局 ID 迁移。

新任务策略为 `vnext-task-policy-57`；发布策略仍为 8。既有 Campaign 不自动新增
Critic／领域／预算策略；已冻结任务或知识应使用相符运行时，不改写其身份来迁移。
可执行命令及 JSON 契约见[操作手册](../ORCHESTRATOR_RUNBOOK.md#optional-coverage-and-delivery-pilots)。
