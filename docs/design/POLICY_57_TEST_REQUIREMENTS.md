# Policy 57 改造测试需求

版本：1.0
基线：运行时 task policy 57、release policy 8；改造提交 `f3897ef`
状态：工程测试需求；不代表真实项目效果或发布验收已经完成

## 1. 目的与范围

本文把 policy 57 的运行时改造转成可验证需求，为后续回归、获授权的真实项目
开发试测、独立效果评估和宿主验收提供统一判据。对应测试步骤见
[Policy 57 改造测试计划](POLICY_57_TEST_PLAN.md)。

范围包括 Coverage Critic 与覆盖计划扩展、领域指导、未决项结构化交付、
Campaign 任务预算准入、安全产物转存及隔离接口、Skill 使用入口，以及兼容性。
README 的发现性和 GitHub 元数据不作为安全功能验收；Skill 元数据只做格式和
发现性回归。

## 2. 术语和验收层级

- **声明**：Agent、协调器或操作者提供并通过结构校验的值；不自动等同于真实阅读、
  真实独立性、组织授权或语义正确。
- **本地验收**：单元、集成、故障注入、并发与回归测试证明仓库代码路径的行为。
- **开发试测**：在获授权冻结的真实源码上观察工作流缺陷；不能单独证明召回率、
  精确率、跨语言能力或发布资格。
- **独立效果验收**：标签与答案隔离、盲评、配对且预算相当的发现／分诊试验。
- **宿主验收**：由真实宿主证明身份、上下文隔离、进程控制、资源限制或文件读取边界。

每个需求的状态必须分别记录为 PASS、FAIL、BLOCKED 或 NOT RUN；跳过不等于 PASS。
测试证据至少保存代码 SHA、策略版本、命令、环境、结果、失败／跳过原因和
相关输入／产物摘要。不要在仓库提交秘密、测试目标的受限答案或个人数据。
